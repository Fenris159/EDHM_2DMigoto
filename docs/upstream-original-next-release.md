# Original 3Dmigoto: next EDHM release intake

**Verified:** 2026-11-12. **EDHM source:** `34d92f27f588bbc3f72320c0fa17b674638698c6` (same runtime code as local release v0.1.3). **Original source:** `8f329bd94fecc9bbcb9211ffd42a95dd7fe6b43e`. **XXMI source:** `065dc746c21c71ef48bbc93cb6b90b3dcdf766e6` / v1.2.3.

## Decision brief

Original 3Dmigoto has **one new non-merge source change after 1.4.9**: [f63fe792](https://github.com/bo3b/3Dmigoto/commit/f63fe792052059f1e58ee3d9f0f40967c430d68b), raw-buffer and Texture1DArray support in the HLSL decompiler. **Neither current EDHM nor XXMI v1.2.3 contains that implementation.** It is an optional shader-hunting/tooling candidate, not an established performance improvement, and needs adaptation before shipping: raw load component/operand handling is incomplete for the full instruction contract, upstream did not establish successful shader round trips, and the patch does not apply cleanly to current EDHM formatting/modernization.

Two small original changes also remain absent: decouple `HookedContext.h` from the hook-library header ([32d6670d](https://github.com/bo3b/3Dmigoto/commit/32d6670d079c195cbb70a35d2dcf6c273fa36ec3)), and explicitly include the shell API where NVAPI profile elevation uses it ([91986f01](https://github.com/bo3b/3Dmigoto/commit/91986f015908592c60b16f911a876b5f508fef02)). Both are optional build hygiene; neither should be sold as a runtime gain. The original ShaderRegex parse-crash fix and D3D11On12 export are **already present through different XXMI commits**, with additional EDHM export guards. Skip those duplicates.

For the next release, prioritize the separate XXMI correctness/performance shortlist and keep original intake small: optional header hygiene, then a separately validated decompiler adaptation only if the release intends to improve shader hunting. Do not merge original's dependency/project-layout migration wholesale.

## 3. Decompiler candidate O03: what to adapt before shipping

### Verified local/XXMI gap

The original patch adds **57 lines and removes 1**, all in `HLSLDecompiler/DecompileHLSL.cpp`; it has no dependency on the later original build migration beyond source context already in its parent. Current EDHM instead has:

- `ReadResourceBindings` supports `1d`, `2d`, `2darray`, etc., but lacks `1darray`.
- `ParseCode` recognizes neighboring texture and structured-buffer declarations, but lacks `dcl_resource_texture1darray` and `dcl_resource_raw`.
- `OPCODE_LD_RAW` remains grouped under an unsupported-instruction comment, alongside raw stores/UAV instructions.

The same missing handlers were verified in XXMI `065dc746...`, using source search and the direct file diff against original master. A ByteAddressBuffer name/type in another part of the file does **not** establish this patch is present. [Current bindings parser](https://github.com/Fenris159/EDHM_2DMigoto/blob/34d92f27f588bbc3f72320c0fa17b674638698c6/HLSLDecompiler/DecompileHLSL.cpp#L991), [current declaration parser](https://github.com/Fenris159/EDHM_2DMigoto/blob/34d92f27f588bbc3f72320c0fa17b674638698c6/HLSLDecompiler/DecompileHLSL.cpp#L4931), [unsupported raw load](https://github.com/Fenris159/EDHM_2DMigoto/blob/34d92f27f588bbc3f72320c0fa17b674638698c6/HLSLDecompiler/DecompileHLSL.cpp#L7413), [XXMI file](https://github.com/SpectrumQT/XXMI-Libs-Package/blob/065dc746c21c71ef48bbc93cb6b90b3dcdf766e6/HLSLDecompiler/DecompileHLSL.cpp).

### Upstream validation is partial

The [author's PR384](https://github.com/bo3b/3Dmigoto/pull/384) reports getting past the two declarations in a DMC5 shader, then failing recompilation on an unrelated packed-cbuffer swizzle problem. The maintainer accepted the improvement without validating functional generated HLSL. [Issue385](https://github.com/bo3b/3Dmigoto/issues/385) remains an example of that separate decompiler limitation; do not count the raw-buffer patch as a fix for it or copy the issue's proposed expected swizzle as a validated specification.

### Source-level adaptation risks

1. **Vector raw loads need proper component semantics.** Upstream always emits `.Load(...)` then a resource swizzle. Microsoft specifies `ld_raw` can read one through four 32-bit components and apply a source swizzle/write mask; `ByteAddressBuffer.Load` returns one scalar `uint`, while `Load4` returns `uint4`. **Inference from source plus the API contract:** a generic translation cannot implement every vector/raw swizzle by blindly using scalar `Load`. Select the correct load width/address and preserve bits, resource swizzle and destination mask. [Instruction contract](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/ld-raw--sm5---asm-), [scalar load](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-byteaddressbuffer-load), [four-component load](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-byteaddressbuffer-load4).
2. **Operand classes are broader than `t#`.** Microsoft permits `t#`, `u#`, and `g#` in applicable shader stages. Upstream's new path parses only `t%d.` and does not check the scan result before using its register variable. An adaptation must initialize/check parsing and dispatch by the correct resource class, or explicitly preserve unsupported-output behavior for forms not implemented. This is a source-level compatibility concern; no native failing shader was executed in this intake audit. [Patch](https://github.com/bo3b/3Dmigoto/commit/f63fe792052059f1e58ee3d9f0f40967c430d68b).
3. **Preserve EDHM hardening.** The patch uses raw `sprintf` and older local buffers. Current EDHM uses bounded output helpers, initialized parse values and other modernized ownership/type handling. Manually carry the behavior into those conventions rather than replacing the file or weakening warning policy.
4. **Declaration support is not complete shader translation.** Texture1DArray reflection/declaration support must also round-trip the shader's actual sample/load/resource-dimension operations. Raw stores are still unsupported. Test only the support actually implemented; do not advertise general shader-model-five/raw-resource completeness.
5. **Renderer impact is conditional.** These routines run when decompilation/hunting/export/automatic shader repair needs them. Existing hand-authored EDHM replacements do not get faster simply because a new resource declaration can be decompiled. Proton relevance is tooling compatibility through Wine's D3DCompiler path; no Elite shader fixture proving need or gain was identified by this source review.

### Reviewable split for O03

- **O03a:** port Texture1DArray reflection/declaration handling from [f63fe792](https://github.com/bo3b/3Dmigoto/commit/f63fe792052059f1e58ee3d9f0f40967c430d68b), preserving current safe formatting. Validate named and stripped bindings, dimensions and representative sample/load behavior.
- **O03b:** add initialized/checked raw SRV declaration handling and deliberate scalar/multi-component raw-load translation. Treat UAV/shared-memory forms explicitly. Retain unsupported comments for forms outside implemented scope instead of generating misleading HLSL.
- **O03c:** validate decompile → D3DCompile → execution/result equivalence on known fixture shaders, including component masks, swizzles and absent/invalid metadata. A syntactically valid recompile alone is weaker than correct resource reads.

These are **suggested future implementation units**, not changes made in this audit. O03a/O03b cite the same source commit but can be reviewed and validated separately. Added tests would follow the repository's behavior/case agreement and deliberate-break verification policy; no new tests were written here.
