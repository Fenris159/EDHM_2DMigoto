# Upstream release baselines and optimization audit

Audit date: **2026-11-12**. Local source snapshot: `34d92f27f588bbc3f72320c0fa17b674638698c6`. This is the upstream evidence supplement to the local code/performance audit. No production code, existing work, local branches, or remote-tracking refs were changed by this research.

## Brief

The configured XXMI upstream is **SpectrumQT/XXMI-Libs-Package**. Its latest published release is **v1.2.3**, substantially newer than the repository's previously fetched **v0.9.8** tag. For original 3Dmigoto there are two legitimate baselines: **1.3.16**, GitHub's latest non-prerelease, and **1.4.9**, its newest published build, explicitly a beta. Treating the old locally fetched XXMI tags as the latest release would miss several performance candidates.

The strongest new candidates are earlier buffer exits in hash-contamination tracking, parser work reduction, per-resource TextureOverride candidate caching, adjacent slot batching, cached-data reads for `store`, and compatible source-view reuse. **No per-change game timing, frame-rate gain, or speedup percentage is established by the upstream evidence reviewed here.** Candidate order therefore follows observable hot-path work removed, integration risk, and workload relevance; it is not a measured performance ranking.

Two compatibility traps affect adoption. Upstream TextureOverride caching always combines hash and fuzzy candidates and drops matching for untracked resources; EDHM restores hash-first behavior and may require the uncached fallback. Conditional slot batching initially crashed and was reverted; only its corrected series is a suitable candidate. The local EDHM real-input-layout side-car design also must survive any import of upstream layout caching.

### Comparison accounting

- `v0.9.8..v1.2.3`: **241 commits, 183 non-merge commits**, **68 files**, **10,526 insertions / 1,276 deletions**. These are revision-range statistics, not performance measurements.
- `HEAD...v1.2.3`: **163 local-only / 296 upstream-only commits**; merge base `af232a90...`. Cherry-picks/manual ports preserve changes without preserving ancestry, so these counts are **not** counts of missing features or missing patches.
- Original stable→beta is a historical toolchain/runtime/decompiler change range. Original beta→live master contains the raw-buffer/Texture1DArray decompiler change and its merge; no further optimization is established there.
- XXMI release→live master has **zero commits** as checked. “Since the latest XXMI release” thus means comparing the local code to that release, not pretending an upstream post-release optimization range exists.

### What upstream actually claims

The examined [parser PRs](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/22), [lookup/dispatch PRs](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/30), [buffer-exit PR](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/44), [profiler PR](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/45), [batching PR](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/46), and [candidate-cache PR](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/47) explain work reduction but provide no controlled per-change benchmark tables in the PR bodies read. Source comments saying a cost was measurable do not supply the missing numbers. The shader binding cache contains commented benchmarking scaffolding, not captured timing results.

Published release notes identify [cache-first store/batching/fuzzy matching in v1.2.0](https://github.com/SpectrumQT/XXMI-Libs-Package/releases/tag/v1.2.0), [view reuse in v1.2.2](https://github.com/SpectrumQT/XXMI-Libs-Package/releases/tag/v1.2.2), and [region/stream-output fixes in v1.2.3](https://github.com/SpectrumQT/XXMI-Libs-Package/releases/tag/v1.2.3). They do not quantify FPS or CPU-time gains for individual changes.

## 5. Adoption order justified by current evidence

1. **Establish repeatable baselines and correctness first.** Save local/beta/stable/XXMI DLLs and matching INIs/shader sets; record compiler flags and native dependencies. Preserve EDHM-specific behavior. Address applicable region, pool flag/lifetime and shader-error-blob fixes (U17, A12 and [shader blob fix](https://github.com/SpectrumQT/XXMI-Libs-Package/commit/7ff1fe7b1f7f1914abad0bd2644bde3cae3dfc68)); safety fixes do not need an FPS claim.
2. **Add observability, then the smallest hot-path candidate:** profiler split counters where useful, U11 for profiling overhead, U10 buffer early exit. These are small enough to isolate and have limited parser/execution dependencies. Report profiling-off frame timing separately.
3. **Apply load/reload optimizations independently:** U01, U08, U02, U03, U04, U05; then consider U06/U07 if their specific line/include work is material. Time each before building a cumulative stack. Review diagnostics/Unicode/namespace behavior. This order favors large algorithmic work removal over tiny comparison changes.
4. **Port U12 as an EDHM-specific implementation.** Keep hash-first and opt-in dual matching, untracked-resource fallback, local lock/lifetime rules and correct invalidation. Test resource churn, hash updates and config reload. Use candidate rebuild/lookup counters to confirm value.
5. **Port U16 and U13**, measuring separately. For U13 keep fixed-slot eligibility, order, null/gap semantics and COM references. U16 is useful only when source views can actually be reused; U13 only when command lists contain qualifying runs.
6. **Consider U15 only for demonstrated `store`/hash readback pressure.** It may move cost into all writes and consume substantial RAM; do not globally enable all buffer caches based on a `store`-only microbenchmark.
7. **Adopt U14 only after U13 is stable**, from the corrected [PR68](https://github.com/SpectrumQT/XXMI-Libs-Package/pull/68) series. Test slots above zero, missing else, nested branches, pre/post and conditions that read resource state.
8. **Defer language/API expansion and tooling migrations** until a mod or support need justifies them: bytecode reflection, dynamic/range syntax, color/input options, full layout-cache replacement, wholesale dependency/project imports. They increase the behavioral surface and cannot be ranked as proven performance gains.

If a measured workload identifies a dominant hot path, reorder the corresponding candidate ahead of lower-impact work while respecting dependencies. Do not sum per-change percentages: caches/batching/parser changes interact, and later gains are measured against a different baseline.

## 6. Measurement and attribution rules

Each U/H item needs an immutable old/new source pair and a single changed mechanism. Whole-release FPS comparisons confound defaults, feature removal, logging, toolchains, dependencies, mod semantics and accumulated fixes. Use the same game scene, renderer, driver, settings, shader files, INI values and thermal state. Capture frame-time distribution and CPU/GPU bottlenecks, not FPS alone. Startup/reload improvements are reported in milliseconds for that operation; allocation reductions are bytes/counts; profiling-overhead savings are labeled profiling-only.

For each pair, use warm-up then repeated interleaved A/B runs, retain raw per-run observations, and report medians plus uncertainty. Establish a minimum detectable effect from run-to-run noise. A failed, unsupported or unmeasured comparison is **not** zero improvement. A portable algorithm benchmark is not a D3D11/Elite Dangerous performance result. CPU cache/staging tests must include invalidations and write overhead. Validate observable output/matching semantics before calling an optimization successful.
