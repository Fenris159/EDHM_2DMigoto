# Releasing EDHM_2DMigoto

## Version numbers

| Location | Purpose |
|----------|---------|
| **`VERSION`** | Package / GitHub Release SemVer (`0.1.1`, `0.1.1-beta.1`) |
| **`version.h`** | DLL *file* properties (keep in sync with `VERSION`: MAJOR.MINOR.PATCH) |
| **Tags** | `v0.1.1` (release) · `v0.1.1-beta.1` / `v0.1.1-rc.1` (pre-release) |

Follow [Semantic Versioning](https://semver.org/) and [Keep a Changelog](https://keepachangelog.com/).

## Files

| File | Role |
|------|------|
| `CHANGELOG.md` | Full history (`## [Unreleased]`, `## [X.Y.Z] - date`, …) |
| `CURRENT_RELEASE_NOTES.md` | Body used by the Release workflow for GitHub Release notes |
| `scripts/version.ps1` | Bump VERSION, compute tags, sync notes from CHANGELOG |

Before a cut, update **CHANGELOG** (move Unreleased items into a version section), then either:

```powershell
.\scripts\version.ps1 -Action sync-notes
```

…or let the Release workflow run `sync-notes` for you.

## Channels

| Branch | Workflow result | Tag style |
|--------|-----------------|-----------|
| **`main`** | **Release** (stable) | `vMAJOR.MINOR.PATCH` |
| **`develop`** | **Pre-release** | `vMAJOR.MINOR.PATCH-beta.N` (or `-rc.N` / `-alpha.N`) |

## Manual release (GitHub UI)

1. Ensure the branch has `EDHM_2DMigoto.sln` (not scaffold-only `main`).
2. **Actions → Release → Run workflow**
   - GitHub's **Use workflow from** selector chooses the revision of
     `release.yml` to run.
   - The workflow's **branch** input chooses the source branch to check out,
     tag, build, and update.
3. Choose:
   - **branch**: `main` or `develop`
   - **version_action**: `use-current` or a bump
   - **pre_label**: `beta` / `rc` / `alpha` (`develop` only)
   - **create_tag**: usually `true`
   - **update_vendor_cache**: usually `true` (skips on draft)
4. Workflow will:
   - Optionally bump `VERSION`
   - Refresh `CURRENT_RELEASE_NOTES.md` from `CHANGELOG.md`
   - Commit + push if needed
   - Create annotated tag
   - Build **Zip Release | x64**
   - Publish GitHub Release with `d3d11.dll`, `d3d11_edhm.dll`,
     `edup-runtime.json`, ZIP and SHA256 files
   - Update **`vendor/edhm-runtime/`** and **`vendor/edup-runtime/`**
     (DLLs via Git LFS + metadata) on the selected branch when permitted

Tags are repository-wide. Never reuse an existing release or pre-release tag.
The preserved `linux-compatibility` branch is the source for the stacked review
branches; it is not an additional release-workflow channel.

## Stable releases with protected main

`main` requires a PR and passing checks, including for repository administrators.
Prepare the stable `VERSION`, its dated changelog section and matching
`CURRENT_RELEASE_NOTES.md` on `develop`, then promote `develop` through a PR to
`main`. Keep `version.h` at the same MAJOR.MINOR.PATCH as `VERSION`.

Run **Release** from `main` with `branch=main`, `version_action=use-current`,
`create_tag=true`, `draft=false`, and `update_vendor_cache=false`. Preparing the
version and notes before promotion lets the workflow tag/build/publish without
needing a direct version/notes commit to protected `main`.

After publication, put the exact downloaded release DLL and its generated
metadata in `vendor/edhm-runtime/` and `vendor/edup-runtime/` on a branch based on `main`.
The EDUP copy is named `d3d11_edhm.dll` and its `manifest.json` matches the
published `edup-runtime.json`. Both DLLs must have identical SHA256 values. Open and check a
follow-up PR to `main`, then merge it. Verify the cache's SHA256, tag, channel
(`release`) and URL against the published assets. The normal main-to-develop
sync includes both release-promotion and cache merge commits in `develop`.

Prerelease cache updates on `develop` can continue using
`update_vendor_cache=true`. Keep the branch protection enabled throughout.

## EDUP updater assets

Each release publishes `d3d11_edhm.dll`, its `.sha256` file and
`edup-runtime.json` alongside the ordinary runtime package. The manifest is
generated by `scripts/write-edup-manifest.ps1` from the built DLL and names a
tag-pinned download. EDUP can use the permanent
[`releases/latest/download/edup-runtime.json`](https://github.com/Fenris159/EDHM_2DMigoto/releases/latest/download/edup-runtime.json)
URL to discover stable updates independently of the cache PR. Verify the
manifest version, tag, channel, size and SHA256 against the published asset
before updating either vendor folder.

## Crash symbols

Optimized Release and Zip Release builds emit `3Dmigoto.pdb` and `d3d11.map`
while retaining COMDAT folding and reference optimization. Each release also
publishes `EDHM_2DMigoto-<tag>-x64-symbols.zip` and its SHA256. The ZIP contains
the exact built DLL, PDB, map, runtime provenance manifest and license notices.
The same PDB matches both runtime filenames because their DLL bytes are
identical. Keep the matching binary and symbols when investigating a dump;
rebuilding the same source does not guarantee a matching PDB identity.
The ordinary runtime ZIP remains the installation package.

## CI

**Actions → CI** runs for PRs targeting **`develop`** or **`main`**, pushes to
**`main`**, and **workflow_dispatch**:

- Meta checks (`VERSION`, changelog, release notes)
- Pinned native formatting and PowerShell analysis
- Strict Windows MSBuild **Release | x64** and **Release | Win32** when the solution exists
- Ordinary **Release** and **Zip Release** builds on **x64** and **Win32**
- Optional strict **Zip Release** builds on both platforms with the manual `zip_release` input
- Uploads `d3d11.dll` as a workflow artifact (14 days)

It does **not** run on every commit to `develop`. Use **Actions → CI → Run workflow** if you need a build before merge.

Scaffold-only `main` skips compile but still runs meta checks.

## Sync main → develop (after PR merges)

Workflow: **Sync main into develop** (`.github/workflows/sync-main-to-develop.yml`)

GitHub merge commits live only on `main`, so after a develop → main PR the three-dot
count shows **main ahead / develop behind** even when all feature work is merged.
This workflow runs on **push to `main`** (and manual dispatch) and:

1. If tips match → no-op  
2. If `develop` is an ancestor of `main` → **fast-forward** `develop` to `main`  
3. If histories diverged cleanly → merge `main` into `develop`  
4. On conflict → fail (resolve locally)

That keeps the branch-status badges and GitHub’s “behind” UI honest without
polluting `main` with badge-bot commits.

## Branch protection (GitHub)

Configured for the four long-lived branches (`main`, `develop`, `xxmi-base`, `badges`):

| Branch | Delete | Force-push | How to update |
|--------|--------|------------|----------------|
| **main** | Blocked | Blocked | **PR required** (0 approvals for solo); CI checks **Meta checks** + **MSBuild (Windows)** |
| **develop** | Blocked | Blocked | Direct push OK (daily work); Release Action may commit with admin/token as needed |
| **xxmi-base** | Blocked | Allowed | **Mirror only** — advance via **Update xxmi-base** Action; no feature PRs (see protect-xxmi-base workflow) |
| **badges** | Blocked | Allowed | Bot tip for Shields JSON only; do not merge into main |

`enforce_admins` is on, so these rules apply even to the repo owner (prevents accidental branch delete). To force-push `develop`/`main` in an emergency, temporarily disable that branch’s protection in **Settings → Branches**, then re-enable.

**xxmi-base:** GitHub personal repos cannot restrict pushes to “Actions only” the way org rulesets can. Protection blocks **deletion** and a workflow **fails any PR targeting `xxmi-base`**. Treat the branch as read-only comparison code: never land EDHM features there.

## Vendor caches

After a **non-draft** Release succeeds, the same workflow (when `update_vendor_cache` is true, default) updates both folders:

| Path | Contents |
|------|----------|
| `vendor/edhm-runtime/d3d11.dll` | Built DLL (**Git LFS**) |
| `vendor/edhm-runtime/d3d11.dll.sha256` | Checksum |
| `vendor/edup-runtime/d3d11_edhm.dll` | Identical DLL with EDUP chain filename (**Git LFS**) |
| `vendor/edup-runtime/d3d11_edhm.dll.sha256` | Checksum with renamed filename |
| `vendor/edup-runtime/manifest.json` | Same content as the published `edup-runtime.json` |
| `vendor/edhm-runtime/VERSION` | SemVer without `v` |
| `vendor/edhm-runtime/SOURCE_TAG` | e.g. `v0.1.0-beta.1` |
| `vendor/edhm-runtime/CHANNEL` | `release` or `prerelease` |
| `vendor/edhm-runtime/RELEASE_URL` | GitHub Release URL |

- Prereleases update both caches on **`develop`**
- Stable releases update both caches on **`main`** through the protected cache PR
The `VERSION`, `SOURCE_TAG`, `CHANNEL` and `RELEASE_URL` metadata appears in both folders.

- GitHub **Release assets** remain the distribution source of truth; vendor is a convenience mirror

Local helper (after a manual build):

```powershell
.\scripts\update-vendor-cache.ps1 `
  -DllPath 'x64\Zip Release\d3d11.dll' `
  -Version 0.1.0-beta.1 `
  -Tag v0.1.0-beta.1 `
  -Channel prerelease
```
